## 手机使用

1. 保持“行程模式”勾选。设置服务器、限速、方向、采样间隔，以及路线备注。
2. 选择“持续测量，直到停止”，或者输入整次行程的总秒数。行程计时包含连接和断网等待时间。
3. 开始后可随时更改场景标签。没有网络或服务器断开时，位置、无线信号和网络状态继续按独立时间轴写入；有网后尝试恢复测速。速度没有实际输出时不伪造 0。
4. 结束时点“停止”。数据先在手机保存，后台按设置补传。原“导出最后一次日志”仍可导出整次行程，包括独立观测和连接事件。
5. 上传地址和密钥沿用 v0.6，无需更换。默认仅在测速间隙/结束后上传，避免争抢测试带宽。若希望途中同步，勾选“测速期间同步数据块”并点击保存；同步流量会影响测速，配置中会保留启动时的选择。

Android 后台任务可能延迟执行，已封存数据不代表已经上传。界面分别显示待传块、旧测量及需处理的错误数。修正地址/密钥后点击保存可重试失败记录。

## 实现与数据格式

- 一个 `sessions` 记录对应一个行程，配置含随机 `journey_id`。每次连接有独立 `attempt_id`。
- `samples.start_s/end_s` 保留 iperf 连接内时间；`journey_start_s/end_s` 对齐行程时间。原始事件也保留 attempt_id。UTC 和 Android 单调时钟同时保存。
- `telemetry` 保存独立观测（在 `raw` JSON 中）：实际观测时间、连接状态、网络快照、场景、位置与年龄、无线观测与年龄。其 `throughput_bps=null` 表示这行本身不是吞吐测量；吞吐以 `samples` 中的真实区间为准。
- `attempt_events` 保存连接尝试、连接成功、断开、网络丢失/恢复、重试等待、行程开始/结束。v0.7.1 在 Android 默认网络恢复后打断等待并重置退避，立即重试；持续失败等待 1、2、4、最多 5 秒。TCP 连接超时为 3 秒，握手另有约 8–9 秒看门狗；实际重新出速率还需等待服务器释放旧连接及所选采样间隔。
- 无线请求仍约每 5 秒一次，定位请求约每秒一次。设置 0.1 秒独立采集并不表示每次都有新的 GPS 或 SINR；每条保留来源时间与年龄。
- 数据块约每 60 秒或达到 512 KiB 后封存，检查周期 5 秒；个别大记录可使单块超过目标，接口硬上限 2 MiB。封存读取不持有采样的 Java 全局锁，SQLite 使用 WAL；短事务同时提交数据块及各表进度。
- 块一旦生成就保持字节不变。客户端核对服务器返回的块编号和 SHA-256 后才标为上传成功；网络错误重试，单个坏块单独报错而不阻塞其他块。
- 普通模式和旧测量仍使用原 `/api/upload`，保留其 128 MiB / 250000 行上限。行程使用 `/api/journeys/chunks`，不受“整次行程一个大文件”的上传限制。

- 数据块可乱序到达；最终块给出结束状态和最终编号。只有编号 0 到最终编号全部收到，才显示“已完整接收”。该状态表示数据传齐，不代表无线观测没有缺失。

## 当前边界

本版解决网络断开后的续测、独立采集和分块补传；不承诺应用被系统强杀、手机重启后自动继续同一行程。重新打开应用会把未正常结束的记录标为 interrupted 并安排补传。

本版仍使用现有 `dataSync|location` 前台服务，Android 后台运行额度仍适用。没有完成小米 14 的 6–10 小时锁屏、发热和真实高铁隧道验收。[Android 前台服务时限说明](https://developer.android.com/develop/background-work/services/fgs/timeout)

建议先在手机进行 30–60 分钟试采：中途断网一分钟再恢复，确认状态自动恢复、网页最终显示完整接收，再进入城铁实测。
