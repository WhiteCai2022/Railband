# 已知问题与审查入口

这是截至 2026-11-12 的现状清单，不代表这些问题已经修复。请在报告中区分日志事实、源码推断和复现结果。

## 1. 握手失败后的异常区间仍可能进入 samples

一份 v0.7.3 实测日志中，某次连接未收到 start/connected，却在握手超时清理时输出 interval：`start=0`、`end≈345077.25`、`seconds≈345077.25`、`bytes=0`。整个行程只有约 2.3 小时。

`JourneyRun.runAttempt` 接受 interval 时没有先检查 connected，也没有将原生时间与当前连接实际时长作上界比较。`Store.sample` 直接保存；`LiveRates` 与服务端 `detail_data.py` 的累计秒数会被污染。

审查目标：失败状态的报告如何保留在原始 events，却不作为有效 samples 累计；同时保留真正的长合并区间和合法短尾段。不要简单规定所有区间必须恰好一秒。

人工构造的最小格式样本：[synthetic-invalid-interval.jsonl](../server/fixtures/synthetic-invalid-interval.jsonl)。它不含真实行程；用于验证时间校验条件，不是原生故障复现证据。

## 2. 长途采集存在整体空档

同一份实测日志中，telemetry 出现过约 124、94、44 秒空档；原生报告也出现过 124 秒、44 秒的合并区间。配置 15 秒的停滞检测曾在距最近进展约 128 秒后才执行。

`JourneyRun` 中监控与环境快照共享单线程 ScheduledExecutorService。数据库写入、定时任务阻塞、后台限制或设备挂起均需排查；日志本身尚不足以唯一归因。WakeLock 的 120 秒续期也在该监控任务里，值得一起审查。

目标：记录调度迟延和质量事件，区分真实零值、无样本、合并区间与采集暂停，不通过补零制造连续性。

## 3. GPS 与 network 位置的选择过于依赖时间

`Store.location` 按 fix 的单调时间新旧选择最后位置，未综合精度。实测中存在五秒内、精度数米的 GPS 被精度约 550 米的 network 点覆盖的情况。沿用旧位置无年龄硬截止是有意设计，但调用者必须解释年龄，地图和统计不应把沿用点当新定位。

目标：原始观测全部保留，另外定义质量选择规则，不伪造新的 fix 时间。注意 GPS UTC 与手机 UTC 可能有偏差，关联应优先使用本机 elapsed 时间。

## 4. 大量一秒零值尚不能唯一归因

两份 v0.7.3 实测发送端记录的零值比例约为 33.9% 与 72.4%。零值在原始 iperf 中已是 bytes=0，并非 APP 或画图补零。很多零行的 TCP RTT/窗口仍在变化；大量正数发送量按 128 KiB 整块计数，常见约 22/23、44/45 Mbps。

`src/iperf_tcp.c` 在 Nwrite 返回后更新发送计数；这不是每秒实际无线发送量。分块可以解释离散刻度，不能单独证明高比例零值都是正常统计现象，也不能直接认定为服务器限速或某个已知 iperf 缺陷。

优先做手机发送端与服务端接收端逐秒对照，并在固定地点的良好网络下做基线测试。平滑仅用于展示，不能删零或插值来宣称修复测量。

## 已实现的防护

- v0.7.2：主动暂停上传不再触发失败退避；结束/手动触发及时同步，连续处理多个批次。
- v0.7.3：实际字节进展监控、按方向判定、保留原始事件并过滤重复区间；子进程读取 IOException 结束当前尝试而不是整个行程。
- `TransferWatchdogTest`：时间边界、方向、低限速、长统计间隔与重复报告。
- `StallRecoveryTest`：本地代理注入真实数据连接故障，验证原生输出零值时的恢复；全部是模拟器测试，不能代替真机覆盖验证。

建议从这些已知问题出发提可复现的小改动，先用测试证明，再改变统计口径。研究用原始日志未公开，另行授权后再共享。
