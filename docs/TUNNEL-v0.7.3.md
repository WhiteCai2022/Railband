# v0.7.3 隧道后持续零速的自动恢复

更新日期：2026-11-01。APK：`rail-bandwidth-v0.7.3-tunnel.apk`；versionCode 10；原包名和签名。

## 日志证据

用户提供的两份原始 JSONL 均可逐行解析，包含多次手动重启后的会话，不是一文件一次测速。均为 v0.7.2、上行、不限速、1 秒统计。

- 测试线路 A session 10：14:47:39 至 14:52:46 持续收到零字节报告，覆盖约 308 秒；结束前 SS-SINR 18 dB、SS-RSRP −99 dBm，信号年龄约 2 秒。
- session 11 在 14:52:49 重新开始，第一条上行约 67 Mbps。session 10 和 11 的默认网络实例标识相同。这支持旧测速连接停滞的判断，不能据此将前一段零速都视为无线覆盖差。
- session 12：持续零字节约 339 秒，期间仍有信号更新。
- 测试线路 B session 16：一段零速约 53 秒，期间仍有 NR 信号记录；随后出现过 `Stream closed` 导致整段行程失败。其他连接错误及 server busy 也有记录，日志不能唯一定位每次链路故障的底层原因。

## 原因和修改

旧版只监控进程有没有输出。原生 iperf 的发送线程发生错误后，可以结束该线程而主线程继续定时输出 interval；即使每个区间都是 0，APP 的输出超时也不会触发。出隧道后默认网络实例未变化时，也不一定出现 Android 的网络恢复回调。

新增 `TransferWatchdog`，按每一轮连接、每个测量方向统计实际字节进展，不依赖信号强弱作重连判断：

- 至少收到两个不同的零字节区间，并达到无进展时限，才触发连接重建。
- 基准时限 15 秒；至少容纳两次报告及 1 秒余量。
- 很低的用户限速下，考虑原生 128 KiB 块的发送间隔，避免把主动低速误判为故障。
- 双向测量分别检查上下行，一个方向持续无进展也能触发整轮重建。
- 连接重建仍属于同一个行程，原始位置、信号、标签、重试事件继续记录；缺失时间不补零。
- 相同原生起止区间的重复输出保留在原始 events 中，不再重复写入 samples、刷新进展计时或累计平均值。
- 子进程输出管道的 IOException 结束当前连接尝试，自动进入重试，避免 `Stream closed` 直接终止整段行程；数据库或记录解析错误仍按真实错误处理。

该检测指应用报告的字节进展，并不直接测量无线空口吞吐。真实网络完全不可用时，新连接仍会失败。自动重连属于测量过程中的干预，分析连续序列时应结合 attempt_id 和重连事件。

## 新日志字段

会话 config 增加 `zero_progress_timeout_ms`，单位毫秒，保存本次检测时限。

attempt_events.raw 中新增 state=`data_stalled`。detail 仍是字符串，内容为 JSON，包含 reason=`no_byte_progress`、direction_mask（1 上行、2 下行、3 双向）、timeout_ms、upload_age_ms、download_age_ms。只解释 direction_mask 指定的测量方向。后续仍记录 disconnected、retry_wait、connecting、connected。

## 验证结果

- 纯 Java 检查：15 秒边界、真实字节恢复、连接重置、双向独立判定、重复区间、60 秒报告和极低限速均通过。
- 完整回放两份日志，原有持续零速能触发新检测策略。离线回放只验证检测，不声称历史链路已被实际恢复。
- Android 16 模拟器与真实原生 iperf：用本地 TCP 代理断开数据连接，保持控制连接不动；真实得到 16 条零字节报告，新版自动恢复，同一行程约 16.996 秒后重新出现数据。
- 主动关闭客户端输出管道，约 2.058 秒出现新一轮数据，行程继续运行。
- 独立采集持续记录；保存的区间无重复。测试只使用本机模拟器和回环服务器，没有向生产服务器写入测试数据。
